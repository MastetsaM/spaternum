# Spec — Sync spike (before phase 1)

## What and why
A throwaway test of the sync design in [[2026-10-21-sync-rxdb]]: RxDB as the local database in the Tauri app, syncing through pull/push endpoints in FastAPI to Postgres. Phase 1's notes and voice notes depend on this working, so it gets proven first, the same way phase 0 proved mic access. Code is not reused.

Location: `projects/spaternum/src/prototypes/sync-spike/` — `client/` (Tauri app) and `server/` (FastAPI).

## Scope of the test
One synced table, deliberately tiny — `items`:

```sql
CREATE TABLE items (
    id          uuid PRIMARY KEY,       -- generated by the client
    text        text NOT NULL DEFAULT '',
    created_at  timestamptz NOT NULL,
    updated_at  timestamptz NOT NULL,   -- latest write wins
    archived_at timestamptz,
    seq         bigint NOT NULL     -- assigned by the server from a sequence on every write
);
```

- **Server:** FastAPI + psycopg + plain SQL. `GET /items/pull?seq=…&limit=…` returns changes after the last `seq` the client saw (pulling by the client's `updated_at` would miss old offline edits pushed late — see [[2026-10-21-sync-rxdb]]); `POST /items/push` applies client changes with the latest-write-wins upsert. API token header as planned.
- **Server migrations:** `migrate.py` applies `migrations/NNN_*.sql` once each, in order, forward-only — an early trial of the phase 1 pattern ([[2026-10-21-database-access-plain-sql]]). Added during the build and kept with Mihail's OK.
- **Client:** one screen — list of items, add, edit text, archive; an online/offline indicator; sync errors shown.
- **No live stream from the server:** the client pulls every 5 s and as soon as the network returns. Good enough for the test; a server push (SSE/websocket) is a phase 1 question.
- Runs on both the **phone** (APK) and the **PC** (`pnpm tauri dev`), so both webviews are tested.

## Inputs and outputs
- **Input:** add / edit / archive items on either device; network on/off.
- **Output:** the same items on both devices and in Postgres.

## Acceptance criteria (done when…)
1. An item added on the PC appears on the phone, and the other way round.
2. With the phone offline (airplane mode), items can be added and edited; the app still works after being closed and reopened offline.
3. Back online, those changes reach Postgres and the PC without any manual step.
4. The same item edited on both devices while one is offline → after sync, the later edit wins on both devices and in Postgres.
5. Archiving an item on one device hides it on the other.
6. Data in the phone's local database survives closing the app and restarting the phone.
7. RxDB uses only free (Apache 2.0) parts — checked in its repo's license file.
8. Findings are written in the Results section below.

## Edge cases and failure modes to test
- Server down while the phone is online → app keeps working locally, syncs when the server is back.
- Many changes queued offline (e.g. 50 edits) → all arrive, in order, nothing duplicated.
- Clock difference between phone and PC → note whether it affects who wins (latest write wins uses device time).
- App killed in the middle of a sync → nothing lost or duplicated on the next start.

## Out of scope
- Real notes data model, folders, tags.
- Client schema migrations (RxDB schema versions). Server migrations are in scope — see above.
- Docker Compose / deploying to the Pi.
- Audio files.
- Styling beyond usable.
- More than one table.

## Setup (decided 2026-10-21)
- **Server runs on the PC** — throwaway, fastest to iterate; the PC must be on while testing from the phone.
- **Postgres in Docker** (`pgvector/pgvector` image, same as the real deployment) — Docker is needed for phase 1 anyway.
- **Phone → server over HTTPS with `tailscale serve`** — Tailscale gives the PC an `https://<machine>.<tailnet>.ts.net` address with a valid certificate, so the Android app needs no cleartext exception.
- Needs installing on the PC first: Docker, uv. The phone's Tailscale must be connected during tests.
