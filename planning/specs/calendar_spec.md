# Spec — Calendar (draft)

Status: **agreed, 2026-10-29**. All open questions answered (see "Decided 2026-10-29").

## What and why
A personal calendar for daily use on PC and Android, in the style of Teams: **year, month and week views**, with the day split into **15- or 30-minute slots**. It works **offline**, like notes: Mihail shouldn't have to think about the connection (decided 2026-10-29). Repeating events are in from the start.

It moves ahead of [[notes-recordings_spec]] because it's more urgent (Mihail, 2026-10-29).

The calendar UI comes from a library, not from scratch: **FullCalendar v7** for the views and **rrule-temporal** for repeating events. The reasons and alternatives are in [[2026-10-29-calendar-fullcalendar]].

## Decided 2026-10-29
- **Offline:** yes. Events live in RxDB on each device and sync like notes ([[2026-10-21-sync-rxdb]], [[2026-10-20-offline-latest-write-wins]]).
- **Repeating events:** yes, stored as standard repeat rules (RFC 5545 `RRULE`) and expanded with `rrule-temporal`.
- **Reminders / phone notifications:** later, not in this spec.
- **Sync with Google / Outlook / Teams:** no. It's Spaternum's own calendar.
- **Order:** the calendar comes before notes with recordings.
- **Year view:** days with events get a dot; a tap opens that day.
- **Day view:** yes, next to year, month and week.
- **Week start:** Monday.
- **Edit "All" with changed occurrences:** if the time or the rule changes, the exceptions are archived.
- **Colours / categories:** later.
- **New event from a tap:** 30 minutes long.
- **Hours in week/day:** the full 24 h, scrolled to 08:00 when opened.

## Data model
Owned by the new `calendar` module. Plain SQL ([[2026-10-21-database-access-plain-sql]]). One synced table.

```sql
CREATE TABLE calendar_events (
    id             uuid PRIMARY KEY,               -- generated by the client
    title          text NOT NULL,
    notes          text NOT NULL DEFAULT '',       -- free text under the event
    all_day        boolean NOT NULL DEFAULT false,
    start_at       timestamptz NOT NULL,
    end_at         timestamptz NOT NULL,           -- after start_at
    time_zone      text NOT NULL,                  -- IANA name, e.g. 'Europe/Lisbon'
    rrule          text,                           -- NULL = one-off; e.g. 'FREQ=WEEKLY;BYDAY=MO'
    series_id      uuid,                           -- set on an exception: the repeating event it changes
    original_start timestamptz,                    -- set on an exception: which occurrence it replaces
    cancelled      boolean NOT NULL DEFAULT false, -- exception that removes one occurrence
    created_at     timestamptz NOT NULL,
    updated_at     timestamptz NOT NULL,           -- latest write wins
    archived_at    timestamptz,                    -- NULL = active
    seq            bigint NOT NULL                 -- server-assigned on every write; sync pulls by this
);
```

Three kinds of row, all in the same table:
- **One-off event:** `rrule`, `series_id` and `original_start` are NULL.
- **Repeating event (series):** `rrule` is set. `start_at`/`end_at` are the first occurrence; their length is every occurrence's length.
- **Exception:** `series_id` + `original_start` point at one occurrence of a series. It either replaces that occurrence (new time, title…) or, with `cancelled = true`, removes it.

Choices:
- **Exceptions are their own rows**, not a list inside the series row. If one device moves Monday's meeting and another moves Tuesday's while offline, both changes survive. With a list in one row, latest write wins would drop one of them.
- **`time_zone` is stored** so that "every Monday at 10:00" stays at 10:00 after the clocks change (Portugal has summer time). Occurrences are expanded in that zone, not in UTC.
- **No foreign keys** (same reason as notes, [[notes_spec]]): an exception can reach the server before its series.
- **Archive, never delete**, like every module. The server keeps archived rows.
- **The `RRULE` text is the standard format**, so a later export to `.ics` or a switch of library doesn't change the data.

## Views
Using FullCalendar's free views:
- **Year:** 12 small months (`multiMonthYear`). Days with events get a dot. A tap on a day opens the day view.
- **Month:** classic month grid (`dayGridMonth`).
- **Week:** 7 columns with time rows (`timeGridWeek`), all-day events in a strip at the top.
- **Day:** one column with time rows (`timeGridDay`).
- **Slot size:** 15 or 30 minutes, switchable from the view. Saved per device, like favorites ([[favorites_spec]]).
- A **Today** button and back/forward arrows. Weeks start on **Monday**.
- Week and day show the **full 24 h**, scrolled to **08:00** when opened.
- The app opens the calendar on the view used last on that device.

## Creating and editing
- **PC:** click an empty slot to create a **30-minute** event, or drag across slots to choose its length; drag an event to move it; drag its bottom edge to change its length.
- **Phone:** long-press on a slot to create a 30-minute event; long-press an event, then drag, to move it (FullCalendar's touch behaviour). A tap opens the event.
- The **event form** (main area, like the notes editor) has: title, all-day, start, end, repeat, notes. It saves on its own, like notes (no Save button).
- **Repeat** options in the form: none, every day, every week (choose days), every month (same date), every year, plus "every N" and an end (never / on a date / after N times). The rule is written as `RRULE` text, so other patterns can be added later without changing data.
- **Changing one occurrence of a repeating event** asks: *Only this one* / *This and following* / *All*.
  - *Only this one* → writes an exception row.
  - *This and following* → ends the old series the day before (`UNTIL`) and creates a new series from this occurrence.
  - *All* → edits the series row. If the time or the rule changes, the series' exceptions are archived, because they may no longer match an occurrence.
- **Archiving** works the same way: only this one (cancelled exception), this and following (`UNTIL`), or all (the series and its exceptions are archived together and restored together, like a folder in [[notes_spec]]).
- **Archived = locked** (Mihail, 2026-10-29): an archived event, series or exception can't be changed. To change it, restore it from the Archive page first. The server refuses a change to an archived row and sends the archived row back, so the device drops it. This differs from notes, where a later edit brings a note back.
- **On the Archive page** each archived one-off event or series is one entry (a series shows how many changed occurrences were archived with it). Exceptions never show on their own: they come back only with their series.
- **End before start** is refused in the form; the server stores what it gets, like empty notes ([[notes_spec]]).

## Offline and sync
- Same as notes: RxDB collection `calendar_events`, pull/push through the sync helper, SSE for live updates, `serverNow()` for `updated_at`.
- Occurrences of repeating events are **computed on the device**, only for the dates on screen. They're never stored.
- **The year view** is the widest range, at one year. Expanding a year of daily events is ~365 items per series, which is fine.

## Inputs and outputs
- **Input:** create, edit, move, resize, repeat, archive events; switch view and slot size; jump to a date.
- **Output:** year / month / week / day views; event form; archived events on the shared Archive page ([[archive_spec]]).
- **Server:** `calendar` module with pull/push, `list_archived()` and `restore(id)`.

## Acceptance criteria (done when…)
1. Year, month, week and day views work on PC and Android; the week view switches between 15- and 30-minute slots.
2. Events can be created, edited, moved, resized and archived, with the mouse on the PC and by touch on the phone.
3. All-day events show in the all-day strip and in the month/year views.
4. Repeating events (daily, weekly on chosen days, monthly, yearly, every N, with an end) show on the right dates.
5. A weekly 10:00 event stays at 10:00 across the summer-time change in March and October.
6. Changing or archiving *only this one*, *this and following* and *all* each do what they say.
7. With no connection, events can be created and edited on both devices; once back online, the changes reach the server and the other device.
8. The same event edited on two devices: the later edit wins, nothing crashes.
9. Archived events appear on the Archive page; restoring a series brings back its exceptions with it.
10. Tests pass: server (sync, archive, restore) and client (Vitest: occurrence expansion, the three edit modes, the DST case).

## Edge cases and failure modes
- **End before start** → refused in the form.
- **Event across midnight** → shown on both days.
- **An exception arrives before its series** → nothing shows for it until the series arrives. A cancelled exception on its own shows nothing anyway.
- **An exception whose occurrence no longer exists** (the series changed on another device) → not shown; it stays in the database.
- **A rule the device can't read** (corrupt text) → the event shows once at its start, with a mark, and doesn't crash the view.
- **Edited offline on one device, archived on the other** → if the archive reached the server first, the edit is refused and the event leaves the editing device; it stays in the Archive unchanged, and the offline edit is lost.
- **Endless repeats** → fine, since only the dates on screen are expanded.
- **"Every month on the 31st"** → months without a 31st are skipped (standard `RRULE` behaviour).

## Out of scope
- Reminders and phone notifications (later, own spec).
- Sync or import/export with Google, Outlook, Teams or `.ics` files.
- Invites and other people (single user, [[PRD]]).
- Colours, several calendars or categories (later).
- Showing events in a time zone other than the device's.
- Search over events.
- Links to notes, projects or clients (later, through IDs as in [[2026-10-20-architecture-modular-monolith]]).
- FullCalendar's paid views (timeline, resources).

## Results — server (2026-10-29)
Built in `src/server/spaternum/calendar/`; 15 tests in `tests/calendar_test.py` pass. The tests were written from this spec by a separate agent that didn't see the code. Covers the server part of criteria 7–10: sync of one-offs, series and exceptions; latest write wins; an exception arriving before its series; archiving a series archives its exceptions (earlier-archived ones keep their time); Archive page entries and restore.
- Archived rows are locked (added the same day): a change pushed to an archived row is refused; 2 tests cover it (55 server tests in total).
- An exception archived while its series stays active can't be restored on its own; that only happens through *All*, which archives them on purpose.
