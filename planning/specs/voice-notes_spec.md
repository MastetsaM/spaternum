# Spec — Voice notes (phase 1)

> **Draft (2026-10-21).** The open questions at the end need answers before building. Parts that depend on them are marked *(open Q n)*.

## What and why
Record speech from the microphone on Android and the PC, keep it safe on the server, play it back. Works **offline**: a recording made with no connection uploads when the server is reachable. Phase 1 is recording only; transcription comes in phase 2 and analysis/RAG in phase 3 ([[PRD]]). Voice notes are the main raw material for those later phases, so the job of phase 1 is to make sure every recording reaches the server intact.

## How it fits together
- **Metadata** (one row per recording) syncs through RxDB like notes ([[2026-10-21-sync-rxdb]]).
- **Audio** does not go through RxDB. It is a file: saved locally while recording, then uploaded to the server by a separate upload step ([[2026-10-20-audio-opus-files-on-disk]]).
- Local audio lives in Android app storage, and on the PC in `~/Documents/Spaternum/voice-notes/`. All file access goes through the one file interface ([[2026-10-21-local-files-location]], [[2026-10-20-local-files-behind-interface]]).
- Server audio lives on the HDD at `/data/audio/<uuid>.webm`.

## Recording
Settings proven in phase 0 ([[voice-recorder-prototype_spec]], [[TECH]] Audio):
- `MediaRecorder`, `audio/webm;codecs=opus`, `audioBitsPerSecond: 32000` (~200–250 KB/min).
- `getUserMedia` with echo cancellation, noise suppression and auto gain **off**.
- Android manifest: `RECORD_AUDIO` **and** `MODIFY_AUDIO_SETTINGS`.

One file per recording, named `<uuid>.webm`. The metadata row is created when recording **stops** (so a cancelled or failed recording leaves no empty row) — *(open Q 5 may change this)*.

## Data model
Owned by the voice notes module. Plain SQL ([[2026-10-21-database-access-plain-sql]]).

```sql
CREATE TABLE voice_notes (
    id          uuid PRIMARY KEY,              -- generated by the client; also the audio file name
    title       text NOT NULL DEFAULT '',      -- (open Q 1)
    tags        text[] NOT NULL DEFAULT '{}',  -- (open Q 2)
    recorded_at timestamptz NOT NULL,          -- when recording started
    duration_ms integer NOT NULL,
    size_bytes  bigint NOT NULL,               -- size of the local file; the upload is checked against it
    mime_type   text NOT NULL,                 -- 'audio/webm;codecs=opus'
    uploaded_at timestamptz,                   -- set by the SERVER when the file is stored; NULL = not uploaded yet
    created_at  timestamptz NOT NULL,
    updated_at  timestamptz NOT NULL,          -- latest write wins
    archived_at timestamptz,                   -- NULL = active
    seq         bigint NOT NULL                -- server-assigned on every write; sync pulls by this
);
```

Choices:
- **The server path isn't stored** — it's always `/data/audio/<id>.webm`, derived from the id *(open Q 7)*.
- **`uploaded_at` is server-owned.** The push upsert never writes it, so a device can't reset it to NULL. Devices learn about uploads through normal pull.
- **Transcript columns are not added now.** Phase 2 adds them (and the "validate transcript" action) with its own migration.
- **Archive, never delete** — same as notes.

## Upload
- After a recording stops, the client uploads the file with `PUT /voice-notes/{id}/audio` (whole file in one request; 10 minutes ≈ 2.5 MB).
- The server writes to a temp file, checks the size against `size_bytes`, then renames it into place and sets `uploaded_at` (new `seq`, so every device sees it).
- **Same request twice is safe:** if the file is already there with the right size, the server answers success and changes nothing.
- If the metadata row hasn't reached the server yet (RxDB push still pending), the server answers `404` and the client retries later.
- The client retries pending uploads: on app start, when sync comes back online, and after each new recording. A pending upload = a local file whose row has `uploaded_at` NULL.
- Uploads only run from the device that holds the file. The other device just sees the row as "not uploaded yet".

## Local audio lifecycle
Per [[2026-10-21-local-files-location]], the local copy is deleted only when **uploaded + transcribed + transcript validated by Mihail**. Phase 1 has no transcripts, so **in phase 1 local audio is never deleted automatically**.

## Playback
- Local file present → play it (works offline).
- No local file (recorded on the other device, or deleted later) → stream from `GET /voice-notes/{id}/audio` (online only).
- No local file and offline, or not uploaded yet from the other device → Play disabled, with a short reason ("offline" / "not uploaded yet").

## Archiving
Same rules as [[notes_spec]]: archives live only on the server, shown on the shared Archive page; the module provides `list_archived()` and `restore(id)` ([[2026-10-20-architecture-modular-monolith]]).
- The audio file on the server is kept when archived.
- What happens to the **local** audio file when archiving — *(open Q 4)*.

## UI
- **Record / Stop** button with a running timer.
- **List** of active voice notes, newest first: title (or date-time if empty), duration, size, upload state (local only / uploaded), Play, Archive.
- Recordings not uploaded yet are clearly marked — losing the app before upload loses them.
- Online indicator from the last sync result, not `navigator.onLine` ([[TECH]]).

## Inputs and outputs
- **Input:** microphone audio; Record / Stop / Play / Archive; title and tag edits *(open Q 1, 2)*.
- **Output:** Opus files on the device and the server, one metadata row per recording synced to every device, a list with upload state, playback.

## Acceptance criteria (done when…)
1. A recording can be made on Android and on the PC; it shows in the list right after Stop, with duration and size.
2. With no connection, recording and local playback work; the recording shows as "not uploaded".
3. Once the connection returns, the file uploads without any action, the row shows as uploaded on both devices, and the file on the server has the expected size and plays.
4. A recording made on one device can be played on the other (streamed) once uploaded.
5. Uploading the same file twice doesn't duplicate or damage anything.
6. Killing the app during an upload → the upload completes on next start; no half-written file on the server.
7. Archiving removes the voice note from every device's list; the row and the server file stay; restoring from the Archive page brings it back.
8. In phase 1 no local audio file is deleted by the app.
9. Tests for the module's API, the upload endpoint (size check, repeat upload, missing row), sync endpoints, `list_archived()` and `restore()` pass.

## Edge cases and failure modes
- **App killed or crashes mid-recording** → *(open Q 5)*.
- **Phone call mid-recording** → recording continues but is silent during the call (seen in phase 0). Accepted.
- **Mic permission denied** → clear message, no crash (phase 0 behaviour).
- **Upload interrupted** → the server's temp file is discarded; retry starts over.
- **Size mismatch on upload** → server rejects, `uploaded_at` stays NULL, client retries; if it keeps failing, the list shows the error.
- **Server disk full** → upload fails with an error the client shows; local file kept.
- **Local file missing but row says not uploaded** (e.g. app data cleared) → the recording is lost; the list shows it as "audio missing" instead of retrying forever.
- **Very long recording** → *(open Q 3)*.
- **Two devices record at the same time** → separate UUIDs, no conflict.

## Out of scope
- Transcription, transcript validation, deleting local audio (phase 2).
- Analysis / RAG (phase 3).
- Pause / resume within one recording.
- Linking a voice note to a note, project or client.
- Call recording ([[2026-10-20-park-call-recording]]).
- Editing or trimming audio.
- Resumable / chunked uploads — whole-file upload is enough at ~2.5 MB per 10 min.
- Visible audio files on Android (Storage Access Framework — planned upgrade, [[2026-10-21-local-files-location]]).

## Open questions
1. **Title:** optional title field (empty → list shows date-time), or no title at all? *Recommendation: optional title.* Mostly recorded on the go so it'll often be empty, but it's cheap and helps find recordings before transcripts exist.
2. **Organising:** tags like notes, folders, or nothing in phase 1? *Recommendation: tags only.* Same `text[]` pattern as notes; folders add a second tree to maintain, and phase 3 search will matter more.
3. **Maximum length:** no limit, or a cap (e.g. 60 min)? *Recommendation: no limit in phase 1;* at 32 kbps an hour is ~15 MB, which still uploads fine.
4. **Archiving a recording that isn't uploaded yet, or archiving with a local file present:** keep the local file until uploaded and then leave it (the phase 1 "never delete" rule), or delete the local copy once the server has it? *Recommendation: keep the upload going, never delete in phase 1.* Archive only hides the row; the file rule stays simple and in one place.
5. **Crash safety while recording:** save the audio only at Stop (simplest — a crash loses the whole recording), or write chunks to disk every few seconds with `MediaRecorder`'s timeslice so a crash keeps everything up to that point? *Recommendation: chunks every ~5 s.* Recordings are the one thing that can't be retyped; costs some extra code (append to file, create the row at start and finish it at Stop, recover unfinished rows on next start).
6. **PC recording is untested.** Phase 0 only tested Android. The Linux webview (WebKitGTK) handles `getUserMedia` and webm/Opus differently from Android's Chromium webview — it may not record webm at all. Needs a short check on the PC before building. If it fails: record in ogg/Opus on the PC (the server and Whisper accept both), or skip PC recording in phase 1 (PC still plays and manages recordings).
7. **Server path column:** [[TECH]] says the row keeps the file path. This draft drops it and derives the path from the id. *Recommendation: drop it* — one less value that can drift from the real file. Cost: moving audio to a different layout later means a code change, not a data change. If agreed, TECH is updated in the same commit.
