# Sync: RxDB on the clients, pull/push endpoints on the server

Decided 2026-10-21 in conversation with Mihail, conditional on a spike. **Confirmed 2026-10-21** — the spike passed all acceptance criteria on the PC and the phone ([[sync-spike_spec]] Results).

## Decision
- Offline modules use **RxDB** as the local database in the Tauri client (PC and Android), with its HTTP replication.
- The server exposes two endpoints per synced table, written in FastAPI + plain SQL:
  - **pull** — changes since a checkpoint: `WHERE seq > $1 ORDER BY seq LIMIT n`, where `seq` is a number the **server** assigns from a sequence on every write. Not by the client's `updated_at` — see below.
  - **push** — client changes, applied with the latest-write-wins upsert (`INSERT … ON CONFLICT (id) DO UPDATE … WHERE excluded.updated_at > t.updated_at`)
- A small reusable helper builds these endpoints; each module keeps its own SQL.
- Postgres stays the single source of truth. RxDB lives only on the clients.
- Audio files don't go through RxDB — only voice-note metadata; files upload separately.

## Why
- Removes the hardest client-side work: local database, upload queue, retries, pulling other devices' changes, live UI updates in React.
- No extra server service — nothing more to run on the Pi or move to the home server.
- Fits future modules: each new module is one more collection plus the same two endpoints.
- AI, transcription and RAG run on the server against Postgres and aren't affected.
- Low lock-in: the sync protocol is our own endpoints, so replacing RxDB later only touches the clients.
- Core and the HTTP replication plugin are Apache 2.0 (free software rule).

## Alternatives considered
- **PowerSync:** full offline sync Postgres ↔ SQLite, but the self-hosted edition is source-available (FSL), not free software; adds a service container with its own storage; self-hosting is beta.
- **ElectricSQL:** Apache 2.0, but read-path only — offline writes left to us. One unconfirmed source says it was acquired by Databricks (Aug 2026).
- **Own sync (SQLite via Tauri + own outbox):** free and fully understood, but the most code, and it grows with every module.

## Correction (2026-10-21): checkpoints use a server sequence, not `updated_at`
The first version of this record pulled by `(updated_at, id)`. That loses data: `updated_at` is set by the device when the edit is made, not when it reaches the server. Example: the phone edits a note offline at 10:00 and pushes at 12:00; the PC already pulled up to 11:00, so it never asks for anything older and never sees the edit. Fix: every synced table gets a `seq bigint` set from a sequence (`nextval`) on each insert and update; pull by `seq`. `updated_at` stays — it decides who wins a conflict, `seq` decides what to pull.

## Proven in the spike (all ✅)
- RxDB works inside Tauri's webview on Android and on the Linux desktop.
- The free IndexedDB storage (Dexie) persists reliably on Android.
- Offline edit on the phone → back online → change reaches the PC.
- The license file in the RxDB repo matches what its site says.

## Phase 1 additions (from the spike)
- **Server push:** SSE endpoint fed by Postgres `LISTEN/NOTIFY`, used as RxDB's pull stream — near-instant sync instead of polling. The `seq` pull stays for catching up after being offline.
- **Clock drift:** clients estimate their offset from the server's `Date` header and correct `updated_at`.
- **Online indicator** from the last sync's success, not `navigator.onLine`.
- **Open the RxDB database once** (StrictMode runs effects twice in development).

## Consequences
- Easier: offline for every module that needs it, at a fixed small cost per module.
- Harder: schema changes happen in two places — a SQL migration on the server and a versioned RxDB schema with a migration function on the client. One more library with its own concepts (JSON Schema collections, checkpoints, conflict handlers).
- Unknown: whether merging simultaneous edits (CRDTs) is possible in RxDB's free core — not needed now (latest write wins).
